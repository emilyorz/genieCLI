### T0 (unplanned hotfix) — 2026-04-17T11:00+0800

Sam's office `/trino-research` run reported `cpu=0ms wall=0ms rows=0` despite Trino actually executing the query. T1-T4 (banner work) deferred while we ran this down.

- **Diagnostic loop**:
  - `cb5a86b` `scripts/debug-mcp-tools.py` — list MCP tools + show resolver choice
  - `9f402db` add `--probe` mode — dump raw response shape per query
  - `d11f88e` add `--measure` mode — call `_execute_via_mcp` + `_fetch_explain_analyze` + `_measure_mcp` and dump every layer
- **First hypothesis (rejected)**: resolver picks `explain_query` instead of `execute_query`. `--probe` showed the resolver actually picks `execute_query` correctly via the explicit candidates list. Burned ~30 min before ruling out.
- **Second hypothesis (correct)**: server returns metrics dict empty / non-existent; backfill from EXPLAIN ANALYZE text needed.
  - `13dbfab` fix(mcp-trino): backfill server-side metrics from EXPLAIN ANALYZE — added per-run fallback in `_measure_mcp` that calls `_fetch_explain_analyze` when `cpu_time_ms == 0 and peak_memory_bytes == 0`.
- **Sam re-ran → STILL `cpu=0 wall=0 rows=0`**. `--measure` revealed the real chain: `_execute_via_mcp` got `rows=[]` because mcp-trino returns a **bare JSON list** (`[{"Query Plan": "..."}]`) and the existing code only handled `{"rows": [...]}` dict shape. With rows empty, `_fetch_explain_analyze` fell back to the JSON-encoded raw string (newlines as `\n` escape, no real line breaks) → `_parse_explain_stages` found 0 fragments → totals = 0 → backfill wrote 0 → display showed 0.
  - `b3f7566` fix(mcp-trino): handle bare-list response shape in `_execute_via_mcp` — extend to detect `data is list` and treat as rows; infer columns from first row's keys. This restores the full chain.
- **Verify (code track)**: `--measure` after pull → `_fetch_explain_analyze available=True, stages=1, total_cpu_ms≈0.04, total_memory_bytes=132, total_input_rows=1`. Sam confirmed `/trino-research` now shows non-zero numbers.
- **Verify (doc track)**: features/trino-research.md updated with v25 design log entries; features/mcp-banner.md updated with deferred-touchpoint note.

**Side-effect bug also fixed**: the optimizer's `capture_rows=True` equivalence check was always seeing `[]` for both baseline and candidate on this server → silently treating different SQL outputs as "equivalent". Now meaningful.

## Retro

### Worked

- The two-tier debug-script approach (`--probe` for raw shape, `--measure` for full chain) is what made the second bug findable in 30 seconds instead of hours of guessing.
- `_dump`-everything pattern (rows / columns / metrics / error / raw) on a single call cuts diagnostic-pass count in half.
- New spec's promote/park/drop tagging stayed coherent even under mid-iteration scope pivot — Carryover for v26 is unambiguous.

### Failed

- **First hypothesis (resolver picks explain_query) was wrong** — assumed root cause from grep evidence without running a probe first. Cost ~30 min of context and one round of unnecessary diff. — `park age 1/3 — trigger: meta-retro at v30 reviews whether to formalize "always probe before patching MCP-contract assumptions" into AGENTS.md or self-model.md. Until then it's an observation, not a v26 deliverable.`
- **Initial fix (`13dbfab`) shipped without verifying end-to-end** — the backfill code itself was correct, but the upstream `_execute_via_mcp` bug meant it could never receive the data it needed. Sam's re-run was the verification I should have done before declaring "fixed". The unit test passed because the mock fed dict-shape data — exactly the bug we were missing in production. — `promote ⭐ P0 S — Add end-to-end smoke discipline: when fixing an MCP-server-contract bug, the unit test must use the actual server's response shape, not the convenient default. Document this as the first item of v26.`
